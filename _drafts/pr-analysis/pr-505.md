## 페어 고민 (PR body 핵심 발췌)

- 이번 단계에서는 단순히 카드 등록 UI를 구현하는 것보다, **입력값 검증 로직을 어떤 기준으로 분리하고 관리할지**를 가장 많이 고민했습니다.
- 처음에는 각 컴포넌트 안에서 입력값과 에러 상태를 함께 처리하려고 했지만, 그렇게 하면 컴포넌트가 UI 렌더링뿐 아니라 상태 변경, 검증, 에러 메시지 노출까지 모두 책임지게 되어 복잡도가 빠르게 커졌습니다.
- 컴포넌트는 현재 상태를 받아 화면에 보여주고, 훅은 입력 변경과 blur 시점의 검증을 담당하도록 역할을 나누니 코드의 의도가 더 분명해졌습니다.
- 단순히 `isError` 같은 boolean으로 관리하면 에러가 발생했다는 사실은 알 수 있지만, 어떤 이유로 발생했는지 구분하기 어렵다고 생각했습니다.
- 나중에 “전체 카드 정보가 유효한지”, “제출 버튼을 활성화할 수 있는지” 같은 폼 전체 검증이 필요해지면 상태가 여러 훅에 흩어져 있어 조합이 번거로울 수도 있겠다고 느꼈습니다.
