# Q5. 검증 로직과 에러 메시지 책임 — 어느 컴포넌트에 둘까?

## 크루의 질문

> "에러 책임을 어떤 컴포넌트에서 관리할지 고민했습니다." — 윤돌·비비빙 페어

> "input의 검증 규칙 및 로직을 어디에서 관리해야 할지." — 아지·애니 페어

## AS-IS 코드

> 🔍 **읽기 전에 — 한 번 멈춰서**
>
> 페어와 한 가지를 입으로 먼저 꺼내봅니다. 답이 아니라, 지금 우리 *추측*이 어디에 서 있는지 들어봅니다.
>
> `onChange` 안에서 *두 가지 일*이 일어납니다 — 값 저장과 검증. 둘이 *같이 일어나야* 하나요, *따로 일어날 수* 있나요?

```tsx
// src/entities/cardCVCNumberInputs/CardCVCNumberInputs.tsx
  const errorMessage = getErrorMessage();

  return (
    <StyledContainer>
      <label htmlFor="">CVC</label>
      <StyledInputWrap>
        <Input
          value={CVCNumber}
          onChange={(e) => {
            changeCVCNumber("CVCNumber", e.target.value);
            checkValidation({
              length: CVC_NUMBER_LENGTH,
              value: e.target.value,
              type: "CVCNumber",
            });
          }}
          isError={error.CVCNumber !== NO_ERROR}
          width="100%"
          maxLength={CVC_NUMBER_LENGTH}
          placeholder="123"
        />
      </StyledInputWrap>
      {errorMessage ? (
        <StyledErrorMessage>{errorMessage}</StyledErrorMessage>
```

## 공식문서 단서 — *상태로 표현하는 사고*

React 공식문서 [Reacting to Input with State](https://react.dev/learn/reacting-to-input-with-state) ([한글 번역](/react-payments/step1/q09-official-docs-ko/reacting-to-input-with-state))에서:

> *Thinking about a UI declaratively means describing the UI for each visual state rather than micromanaging the UI in response to user input.*

에러도 *시각 상태(visual state)*다. *"이 input이 *유효한지*는 무엇으로 결정되는가"*가 결정 기준 — 그 결정에 필요한 모든 데이터가 *어디에 모여 있는지*가 검증 로직의 자연스러운 자리다.

[You Might Not Need an Effect](https://react.dev/learn/you-might-not-need-an-effect) ([한글 번역](/react-payments/step1/q09-official-docs-ko/you-might-not-need-an-effect))는 한 발 더 — *"렌더링 도중 props/state로부터 계산할 수 있는 값은 useState에 두지 마라"* — 즉 **에러 메시지는 종종 *상태가 아니라 파생값*이다.** `state.cvc`로부터 *지금 유효한가*가 매번 계산되어 표시될 수 있다면, *에러 상태*라는 별도 state는 redundant.

## 추가 읽을거리 — Kent C. Dodds · Dan Abramov

<details>
<summary><b>외부 글 모음 — 펼쳐보기</b></summary>

### Kent C. Dodds — Don't Sync State. Derive It!
- 원문: [kentcdodds.com/blog/dont-sync-state-derive-it](https://kentcdodds.com/blog/dont-sync-state-derive-it)
- 한 줄 요약: *에러 메시지를 별도 state로 두고 동기화*하는 대신, 입력값으로부터 *파생*시켜라. 윤돌·아지 페어의 *"에러 책임을 어디서 관리할지"* 질문에 직접 답이 된다.

### Dan Abramov — Before You memo()
- 원문: [overreacted.io/before-you-memo](https://overreacted.io/before-you-memo/)
- 한 줄 요약: 성능 최적화를 위해 `memo`를 쓰기 전에, *상태를 어디로 옮기는가*가 더 큰 영향을 준다. 검증·에러 책임이 어디에 있느냐가 *리렌더링 범위*에 미치는 비용을 다룬다.

</details>
